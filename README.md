# 生成式软件工程

## Lec 1

软件工程研究的是"怎们让工程不失败"。AI可以加速实现，但是却不会暴露未知、分配责任或者验证结果；工程的目的不是让demo跑起来，而是让系统在约束、变化和协作中继续活着。

+ 信息差: 知道哪里不知道
+ 能坐牢: 未取舍承担后果
+ 能驾驭: 让人、Agent与反馈持续对齐目标



稳定、可描述、可验证的重复，本质上就是一个尚未被抽象出来的程序

- Agent 的真正杠杆是**现场制造工具**：把一次性的自然语言需求，变成可重复执行的闭环。
- 可编程性的边界不在“有没有 API”，而在：能否找到**可控输入、可观测输出、可判定的完成条件**。



### 产品是系统性工程

- 前端、后端、交互、运营……任何一个环节做不好，产品都会暴毙
- 虽然 AI 都可以做，但组织不当（让 AI 直接接管组织）也会暴毙
- 产品完成度是乘法：若 10 个环节各有 90% 可靠，整体成功率只有35% 。AI 提高单点产能，不会自动消除接口与协作风险。

### 模型如何补 Gap？

模型补 gap 通过的是**猜**——如果事无巨细都问，人会觉得很讨厌。通过人机协同来解决这个问题

- 目标不是消灭猜测，而是让猜测显式、可逆、可验证：低影响决策先猜后验；高影响、难回滚的决策先停下来问。
- 当 猜错返工澄清 时，应当提问；否则先做最小实验。
- **模型/Agent 很强**，但如何人机协同发挥最大的能力？这就是这门课真正想讨论的

### 软件工程研究什么

工程能力，是在稀疏、延迟的反馈下仍能维持方向；软件工程因此同时组织技术、协作关系、人的动机和时间。

### 怎们让工程不失败

**把不可控的大赌注，改造成可验证的小赌注**

- 拆解：把大“国民级应用”的大 gap 拆成小 gap
- 验证：测试、CI，确保门控
- 迭代：小步提交、快速验证，让噪音尽早暴露
- ……

这不是三条技巧，而是一个反馈控制环：拆解缩短因果距离，门控限制错误传播，迭代提高反馈频率；目标不是零错误，而是错误出现得早、炸得不远、回退得便宜。

### 成本合算方式变了

**“生产”不再稀缺，“验证”成为瓶颈**

- “干能明确描述体力活的码农”变得非常便宜，而且可以 1000X 并行
- 哪怕只有 1% 的垃圾，都会以 10 倍速度膨胀（实际比例更大）
- 瓶颈不再是“生产”，而是“验证”
- 每个人都有机会去解决之前 long-horizon 的问题（短期的时代红利）

### 古法编程死了

禁止古法编程不是禁止理解：先让 Agent 生产，把人的注意力押在定义问题、设计验收和解释失败上。



## Lec 2 Prompt Engineering

### 上下文工程：让模式知道“完成”是什么

Context 里是一份复杂要求

- 模型的潜力完全是靠提示词激发的
- 上下文包含了一个**极为复杂的要求**
  - 约束，可以是 intent，也可以是 spec
- 模型被训练为：持续的Pr[token | context]能不断推进，直到**满足要求**，也就是学会了“规划”的能力

### Intent → Spec → Impl：漂移逐级放大

越明确、越**可验证**的要求，越可能得到你满意的结果

### 新分工：人定义问题，AI 搜索实现

- 明确你的意图，需要你对**产品领域**的知识
- 把意图变成设计，需要你对**软件工程**的知识
- 实现反而多数可以交给 AI，已经超过中级程序员了

### 没有钞能力AI -> 要提出正确的问题，现阶段的AI还是需要引导

你仍然需要“有概念”：对你要实现的东西**有概念**，现在仍然非常重要。Sadly，这只能通过**学习**获得。会用一学期来解释如何用软件工程的方法：给出正确指令、监控 AI 运行、防止 AI 失控……

- 对 CS 学生来说，学科知识体系仍然非常重要：处理器、操作系统、编译器、数据库里有很多**设计智慧**。
- 你需要把模型**引导**到你认为合适的位置上。
- 但你不理解的东西是不能驾驭的。

## Lec 6&7 需求和架构

### Agentic AI：软件生产力的杠杆

**生产目标明确的代码，极为便宜**

- 甚至拥有 Agent Swarm 并行的能力
- Agent 也能写测试用例、断言、甚至是证明

**需求、产品设计、架构**

- **需求、产品设计、架构**成为撬动软件生产力的杠杆
  - 如果不认真对待，就会成为 AI Slop 的堆积

### 软件架构：真正决定软件品味和能走多远的决定性因素

**驾驭复杂性，应对变化**

- 架构使我们驾驭问题的复杂性
  - 能简化问题、安放复杂性、减少依赖
  - 能应对需求的变化、降低维护成本
- 甚至再小的代码都有 “架构”

**把变化安放在边界内**

- 把容易变化的设计决策藏在模块内部，让一次变化尽量只影响一个地方。——[Parnas, 1972](https://ckrybus.com/static/papers/decomposing_systems_into_modules_1972.pdf)

**架构关乎你对需求 “掌控到什么程度”**

**软件工程的本质：驾驭复杂性**

把复杂性分成两类，分别对待：

+ Essential Complexity（本质复杂性）
  + 对应问题域，是问题本身带来的复杂度。
  + 这类复杂性**无法消除**，只能理解它、建模它、正确地表达它
+ Accidental Complexity（偶然复杂性）
  + 对应**技术实现**，是我们选的实现方式额外制造的麻烦。
  + 这类复杂性**可以通过更好的设计、工具、抽象来减少**

出处：Brooks 的 No Silver Bullet

Fred Brooks 在 1986 年的论文《No Silver Bullet》里提出这组区分。他的核心观点是：高级语言、IDE、更好的框架等进步，主要在削减偶然复杂性；但本质复杂性占了软件开发难度的大头，所以不会出现让生产力提升一个数量级的"银弹"。
